먼저 증명

10% 증분 데이터가 실제 API 경로로 정확히 만들어지는지 자동 테스트한다.

동일 조건 비교

cache key·value·TTL·데이터셋·JVM·부하 순서를 고정한다.

결과 전 채택 금지

Redis 사용 경험과 운영 채택을 구분한다. 차이가 작으면 단순한 쪽을 고른다.

구현 원칙

변경하지 않는 것

  • 커밋 조회 API와 응답 JSON
  • MySQL schema와 MongoDB collection
  • 권한 확인과 MySQL 커밋 확인 순서
  • 기존 인증용 Caffeine 캐시

새로 만드는 것

  • 커밋 본문 전용 cache-aside 계층
  • provider별 격리 설정
  • 결정적 증분 seed
  • 부하 실행·결과 판정 자동화
중요: 이 계획은 비교 실험까지다. 최종 운영 TTL, 메모리 예산, eviction과 churn 정책은 측정 승자가 나온 뒤 별도 채택 설계에서 다룬다.

캐시 내부 책임

Cache-Aside

hit면 본문 반환, miss면 기존 assembler 실행 후 성공 결과만 저장한다.

Single-Flight

같은 key 동시 miss만 하나로 합친다. Redis 분산 락은 추가하지 않는다.

Fail-Open

캐시 get·put 오류는 Mongo 원본 경로로 처리한다. 원본 오류는 그대로 API 오류다.

실행 단계

01

실험 계약 고정

기존 GitHub Issue를 확인하고 없으면 범위·판정식을 이슈로 합의한다. 계정 확인 전 assignee를 임의 지정하지 않는다.

Issue 번호 확인
02

데이터 생성 신뢰성

첫 commit은 전체 block, 이후 commit은 10%만 신규 생성하고 나머지는 이전 ID를 재사용한다. 무작위 ID를 제거한다.

Node 테스트 + k6 inspect
03

캐시 코어 구현

none·Caffeine·Redis provider, 인증 캐시 격리, cache-aside, metric, single-flight, fail-open을 테스트 우선으로 구현한다.

단위 테스트
04

실제 경로 연결

CommitService의 기존 권한/MySQL 흐름 뒤에 캐시를 연결하고 삭제 시 best-effort evict를 호출한다.

조회·삭제 회귀
05

로컬 앱·Redis와 부하 도구 검증

현재 소스를 빌드하는 단일 앱을 로컬 Compose에 추가한다. none·Caffeine은 Redis 없이 앱 health가 UP이어야 한다. Redis provider는 warm hit 뒤 Redis 중지·복구까지 확인하고 k6 시나리오와 실행기를 검증한다.

Compose + 통합 + smoke
06

측정·판정·staging

교차 순서로 3회 반복한 뒤 자동 판정한다. 승자 하나만 제한된 staging 조건에서 방향성을 확인한다.

검증 전략

순수 함수·Runner

증분 seed 계산과 함께 mock 명령 기반 shell 테스트로 입력 검증, provider 분기, Redis prefix 정리와 비밀값 비기록을 검증한다.

Java 단위

hit·miss·오류·동시성·삭제 evict와 metric을 원인별로 검증한다.

실제 Redis

Mock만으로 끝내지 않고 JSON, namespace, TTL, stop/recovery를 컨테이너에서 확인한다.

반드시 통과해야 하는 행동

  • 첫 조회만 Mongo 조립하고 두 번째 조회는 hit가 된다.
  • 원본 조회·조립 실패 결과는 캐시하지 않는다.
  • cache get·put 오류가 정상 원본 응답을 실패시키지 않는다.
  • Redis가 중지돼도 앱 health는 UP이며, Redis 장애는 container health와 cache error metric으로 별도 관측된다.
  • 캐시 생성 시 get·put·eviction의 모든 결과 label counter가 0으로 노출된다.
  • 같은 key 동시 20요청에서도 loader가 한 번만 실행된다.
  • 삭제된 commit은 캐시가 남아 있어도 MySQL 확인 단계에서 차단된다.
  • 기존 인증 캐시와 전체 Gradle 회귀 테스트가 통과한다.

Redis health 정책: Redis는 원본 저장소가 아닌 선택적 캐시다. 따라서 Spring Redis health indicator는 기본 비활성화하고, 필요할 때만 MANAGEMENT_HEALTH_REDIS_ENABLED=true로 다시 켠다. Fail-Open 성공은 Redis 중지 중 앱 health UP, 커밋 API 정상 응답, cache error 증가를 함께 확인해 판정한다.

의도적으로 제외하는 범위

이번에 하지 않음

  • 다중 애플리케이션 인스턴스
  • 5,000 blocks 한계 실험
  • Redis 분산 락
  • HTTP ETag와 브라우저 캐시

결과 뒤에 결정

  • 운영 TTL과 메모리 예산
  • eviction과 churn
  • staging Redis 영구 구성
  • 패배 provider 제거 방식

기존 사용자 소유 미추적 테스트 파일은 변경하거나 stage하지 않으며, AI는 별도 요청 없이 commit·push·merge하지 않는다.

실행 전 선택

계획 승인 후 두 가지 방식 중 하나로 실행할 수 있다. 어느 방식을 선택해도 Task 0의 Issue 확인과 승인 gate부터 시작한다.

1. 작업별 분리 실행 · 권장

각 Task를 독립 작업으로 실행하고 구현·요구사항 검토를 단계마다 수행한다. 작업량이 큰 이번 계획에 더 안전하다.

2. 현재 세션에서 순차 실행

여러 Task를 묶어 실행한 뒤 checkpoint에서 검토한다. 문맥은 이어지지만 한 번의 변경량이 커질 수 있다.
