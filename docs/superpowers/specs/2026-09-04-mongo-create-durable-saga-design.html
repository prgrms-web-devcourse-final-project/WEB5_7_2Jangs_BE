MongoDB 생성 정합성 개선

작성일: 2026-09-04. 구현 기준은 refactor/create-durable-saga 작업 트리다. 이 문서는 도입한 구조와 남은 위험을 함께 기록한다.

해결한 문제와 선택

기존 생성 경로는 MongoDB를 먼저 저장한 뒤 MySQL 도메인 엔티티를 저장했다. MySQL 저장이 실패하면 별도 트랜잭션으로 보상 Outbox를 등록했지만 MySQL 장애가 계속되면 이 기록도 유실될 수 있었다.

이제 MongoDB 저장 전에 MySQL에 생성 작업을 기록한다. 여기서 원장은 회계 시스템이 아니라 mongo_create_operation 테이블이다. 어떤 요청이 어떤 MongoDB 데이터를 만들 예정인지, 완료됐는지, 취소 중인지를 보관한다. MongoDB와 MySQL의 로컬 트랜잭션을 순서대로 실행하고 실패를 보상하는 구조이므로 Durable Saga로 분류한다. 이전 구조도 보상 방식의 Saga로 볼 수 있지만 최초 기록이 없어 프로세스 중단과 MySQL 장애를 견디지 못하는 구간이 있었다.

삭제 Outbox는 없애지 않았다. 생성 작업 테이블은 요청의 완료 여부와 결과를 보관하고 기존 Outbox는 실제 삭제와 재시도를 담당한다. 기존 삭제 상태에 생성 성공·응답 재사용까지 넣는 대신 역할을 나눴다. 별도 테이블과 트랜잭션 비용을 감수하는 선택이다.

MongoDB가 MySQL ID를 참조하도록 바꾸더라도 식별자 방향만으로는 두 DB의 완료 여부나 응답 유실을 해결하지 못한다. MySQL만 저장된 상태를 생성 성공으로 취급하지 않으며 이번 작업에서는 참조 방향을 바꾸지 않았다.

식별자와 저장 대상

operationId는 클라이언트가 보내는 UUID 형식의 Idempotency-Key다. 같은 생성 요청의 재시도는 같은 값을 쓴다. MongoDB ID는 서버가 new ObjectId()로 미리 만든다. ID를 만드는 것과 MongoDB에 데이터를 저장하는 것은 별개다.

생성 종류사전 기록하는 새 MongoDB 데이터
문서SaveContent ID 1개
브랜치SaveContent ID 1개
커밋CommitBlockSequence ID 1개와 새로 저장할 Block ID 목록
병합SaveContent ID 1개

기존 커밋에서 재사용하는 블록은 보상 삭제 대상에 넣지 않는다. ID 목록은 mongo_ids JSON 컬럼 하나에 저장한다. 블록마다 MySQL 자식 행을 만들던 초기 구현보다 INSERT 수를 줄였지만 블록 수에 따라 JSON 크기와 직렬화 비용은 늘어난다.

정상 생성과 실패 처리

  1. 도메인 검증과 요청 해시 계산 후 기존 operationId를 확인한다.
  2. 새 요청이면 MongoDB ID를 확정한다. 첫 MySQL 트랜잭션에서 작업을 PENDING으로 저장하고 커밋한다.
  3. 첫 트랜잭션이 성공한 경우에만 사전 ID로 MongoDB 트랜잭션을 실행한다.
  4. 두 번째 MySQL 트랜잭션에서 작업 행을 잠그고 PENDING인지 확인한다. 도메인 엔티티와 작업의 COMPLETED, 결과 ID를 함께 커밋한다.
  5. 예외가 발생하면 별도 트랜잭션에서 COMPENSATING 전환과 COMPENSATE Outbox 등록을 함께 수행한다. 이 등록이 실패해도 앞서 저장한 PENDING은 남는다.
  6. 복구 Worker가 오래된 PENDING을 찾아 같은 보상 등록을 재시도한다. 실제 MongoDB 삭제는 기존 삭제 Worker가 담당한다.
상태의미와 다음 처리
PENDING생성 미완료. 정상 요청은 COMPLETED로, 취소 요청은 COMPENSATING으로 전환
COMPLETEDMySQL 도메인 저장과 완료 표시가 같은 트랜잭션으로 커밋됨. 동일 요청에 결과 ID 재사용
COMPENSATING삭제 Outbox 등록 완료. 이후 같은 키로 생성 재개하지 않음
COMPENSATED삭제 Outbox 완료와 함께 보상 완료 표시
FAILED삭제 Outbox 재시도 소진. 운영 확인 필요

복구 Worker 기본값은 1분 주기, PENDING 제한 5분, 한 번에 최대 100건이다. 행 잠금과 상태 검사는 중복 보상 등록 및 완료 전환의 충돌을 제어한다. 존재하지 않는 MongoDB ID 삭제는 재시도해도 안전하다. 단, 진행 중인 MongoDB 쓰기와 삭제의 경합까지 막지는 않는다.

초기 제안에 있던 “도메인 데이터가 있으면 COMPLETED로 복구”하는 별도 조회는 현재 구현에 없다. 정상 코드에서는 도메인 저장과 COMPLETED가 같은 MySQL 트랜잭션이므로 둘 중 하나만 커밋되지 않는다. 수동 데이터 수정으로 생긴 불일치는 자동 복구 대상이 아니다.

서버가 실패를 확정한 생성은 나중에 이어서 완료하지 않고 취소한다. 다만 브라우저나 프록시의 timeout은 서버가 실패했다는 증거가 아니다. 이미 두 DB 저장을 완료했다면 성공 결과가 남는다. “클라이언트가 실패 화면을 봤으면 반드시 취소”하는 절대 보장은 현재 구현에 없다.

API·Swagger·프론트 계약

아래 생성 API에 UUID 형식의 필수 헤더 Idempotency-Key를 명시했다. Swagger의 /v3/api-docs에서 프론트 클라이언트를 로컬 재생성했다.

POST 경로생성 대상
/api/document문서
/api/document/{documentId}/branch브랜치
/api/document/{docId}/commit커밋
/api/document/{docId}/merge병합

같은 키라도 사용자·작업 종류·요청 해시가 다르면 IDEMPOTENCY_KEY_REUSED(409)를 반환한다. 진행 중이면 CREATE_OPERATION_IN_PROGRESS(409), 취소 중·취소 완료·보상 실패면 CREATE_OPERATION_CANCELLED(409)를 반환한다. 완료 직전 상태가 바뀌면 CREATE_OPERATION_INVALID_STATE(409)가 발생할 수 있다. 문서 생성 성공 응답의 Swagger 표기는 실제 컨트롤러와 같은 201로 맞췄다.

프론트는 문서·브랜치·커밋·병합별로 키를 보관한다. 같은 화면에서 같은 payload를 재시도하면 같은 키를 보낸다. 네트워크 오류와 IN_PROGRESS에서는 키를 유지하고 CANCELLED 응답에서는 키를 폐기한다. 취소 후 다음 수동 요청은 새 생성으로 처리한다. 성공 처리 완료 또는 payload 변경도 새 키를 쓰는 기준이다. 자동 재시도는 추가하지 않았다.

키 저장소는 메모리 기반이다. 새로고침·화면 이탈·컴포넌트 재생성 후에는 유지되지 않는다. 문서 생성 모달을 닫아도 키를 폐기한다. 이때 같은 내용을 다시 제출하면 별도 생성으로 취급될 수 있다. 탭 간 동기화나 영구 재시도 기록은 이번 범위에서 제외했다.

필수 헤더 추가는 구버전 프론트와 호환되지 않는다. 프론트와 API 배포 순서를 맞춰야 한다. 새 프론트가 보내는 추가 헤더는 기존 백엔드에서는 무시하므로 프론트 선배포가 가능한지 배포 환경에서도 확인한다. 로컬 검증은 배포나 실제 사용자 세션 E2E 검증을 대신하지 않는다.

수용한 P1 위험

사용자 결정에 따라 heartbeat·lease·MongoDB fencing·장시간 MySQL 잠금은 추가하지 않았다.

정상 요청이 5분을 넘겨 멈춘 동안 Worker가 먼저 보상 삭제를 끝낼 수 있다. 그 뒤 원 요청이 MongoDB 쓰기를 커밋하면 마지막 MySQL 단계는 PENDING이 아니어서 실패한다. 이미 완료된 보상은 다시 실행되지 않아 MongoDB 고립 데이터가 남을 수 있다. 상태 전환에 건 행 잠금만으로는 이 순서를 차단하지 못한다.

MongoDB 쓰기부터 완료 처리까지 MySQL 잠금을 유지하면 경합을 직렬화할 수 있지만 커넥션 점유와 잠금 대기가 늘어난다. heartbeat는 오판을 줄이지만 긴 프로세스 정지까지 막는 보장은 아니며 fencing은 MongoDB 쓰기 경로까지 바꿔야 한다. 현재 선택은 복잡도와 비용을 줄이는 대신 이 위험을 수용하는 것이다. 5분을 늘리는 것만으로 문제가 해결됐다고 판단하지 않는다.

DB 변경과 운영 확인

V5 마이그레이션은 mongo_create_operation 테이블과 (status, updated_at) 인덱스를 추가한다. 초기의 ID 자식 테이블 설계를 JSON 컬럼으로 바꿨다. V5가 이미 적용된 환경이라면 파일을 덮어 배포하지 말고 별도 후속 마이그레이션이 필요하다. 운영 적용 이력은 이번 로컬 검증만으로 확인되지 않았다.

오래된 PENDING, COMPENSATING 적체, FAILED와 Outbox 실패를 함께 확인한다. COMPLETED 기록의 보관 기간·삭제 정책, 자동 고립 데이터 탐지, 취소 API, 장애 주입을 포함한 지연 요청 경합 테스트는 구현하지 않았다. 원장을 삭제하면 같은 키의 재사용 방지도 사라지므로 보관 정책은 별도 결정이 필요하다.

검증과 작업 기록

2026-09-04 로컬에서 백엔드 전체 테스트 266개가 실패·오류·건너뜀 없이 통과했다. 추가한 OpenAPI 계약 테스트는 네 API의 필수 UUID 헤더와 409 응답을 확인한다. 프론트 키 관리 테스트 4개와 Vite 빌드도 통과했다. 프론트 전체 TypeScript 검사에는 기존 오류 75개가 남아 있고 수정 대상 파일을 변경 전 버전으로 대체해 비교했을 때 새 오류는 없었다. 브라우저 E2E는 실행하지 않았다.

이전 로컬 검증에서는 MySQL 9.4의 Flyway V1–V5 실행과 Hibernate validate를 확인했다. 성능 수치와 한계는 측정 보고서에 기록했다.

AI는 Saga·테스트·성능 최적화·Swagger·프론트 연결과 문서 정리를 보조했다. 사전 작업 기록과 기존 Outbox 재사용을 채택했고 P1 경합 방지 구현은 사용자 판단으로 보류했다. 테스트 통과는 지연 요청 경합의 안전성을 입증하지 않는다. 이 검증 기록을 작성한 시점에는 커밋·배포를 수행하지 않았다.
