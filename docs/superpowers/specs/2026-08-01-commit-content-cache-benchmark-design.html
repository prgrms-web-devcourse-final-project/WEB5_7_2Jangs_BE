커밋 본문 캐시
비교 실험 설계

Redis를 먼저 채택하지 않는다. 증분 저장 구조의 읽기 증폭을 측정하고, 캐시 없음·Caffeine·Redis를 동일 조건에서 비교해 결과로 선택한다.

단일 앱 환경 100·500·1,000블록 3회 반복 Cold·Hot·Mixed Fail-Open

한눈에 보기

운영 구조앱 1대
비교 후보3가지
기본 커밋 수400개
최대 기본 부하200 req/s
핵심 결론
캐시 효과가 측정 오차보다 작으면 도입하지 않는다. Caffeine과 Redis 차이가 작으면 운영이 단순한 Caffeine을 선택한다. Redis는 명확한 성능 또는 메모리 우위와 장애 대응을 증명해야 선택한다.

문제와 판단 기준

확인된 사실

  • 커밋은 생성 후 불변이다.
  • 조회마다 MySQL 1회, MongoDB 2회와 본문 조립이 발생한다.
  • 운영 앱은 한 대이며 Redis는 없다.
  • 현재 트래픽은 거의 없어 무부하 heap만 확인됐다.

측정해야 할 것

  • 블록 수에 따른 p95·처리량 변화
  • 반복 조회에서 MongoDB 비용 비중
  • Caffeine의 heap·GC 영향
  • Redis의 네트워크·직렬화 비용
운영 컨테이너의 무부하 heap 사용량 67.5MiB는 참고값일 뿐이다. 트래픽이 없는 시점의 값으로 캐시 필요성이나 메모리 문제를 판단하지 않는다.

선택한 아키텍처

캐시는 API 응답 전체가 아니라 MongoDB에서 조립된 커밋 본문에만 적용한다.

1문서 확인기존 서비스 흐름 유지
2MySQL 조회Commit과 commitMongoId 확인
3캐시 조회key = commitMongoId
4MongoDB 조립miss일 때만 CBS + Block
5응답기존 CommitResponse 유지
Cache hit MySQL 확인 후 조립된 List<Map<String, Object>> 본문을 바로 반환한다.
Cache miss CBS와 Block을 조회해 순서대로 조립하고 캐시에 저장한 뒤 반환한다.
고정 경계
cache name은 commitContentCache, key는 commitMongoId, value는 조립 완료 본문이다. 사용자·문서별 응답 DTO 전체를 캐시하지 않는다.

대안 비교

접근법장점문제결정
조립 본문 Cache-Aside MongoDB 조회와 조립 비용에 경계가 정확히 맞음 miss는 기존 비용, 큰 값은 메모리 점유 선택
CommitResponse 전체 캐시 구현이 단순함 API DTO·요청 문맥과 캐시 결합 제외
완성 Snapshot 저장 Cold 조회까지 단순화 저장 중복과 이종 DB 쓰기 복잡성 증가 후속 대안

캐시 동작 정책

저장하지 않음

CBS·Block 누락, MongoDB 오류, 조립 예외, null 결과는 캐시하지 않는다.

Single-flight

같은 key의 동시 miss는 앱 내부에서 한 번만 조립한다. Redis 분산 락은 쓰지 않는다.

삭제

단일 커밋 삭제는 best-effort 제거한다. 실패해도 삭제 트랜잭션을 실패시키지 않는다.

실험 통제값

TTL저장 후 10분60초 측정 중 만료 방지
논리 key 수최대 400개주 비교 중 eviction 방지
Caffeine최대 400항목앱 heap 변화 측정
Redis전용 namespace주 비교 중 maxmemory eviction 없음

이 값은 운영 정책이 아니다. 운영 TTL과 메모리 예산은 결과가 나온 뒤 별도 설계에서 정한다.

장애 처리

캐시는 보조 계층이고 MongoDB가 원본이므로 Fail-Open을 적용한다.

캐시 정상캐시 본문 반환
캐시 조회 오류·timeoutMongoDB 원본 조회
캐시 저장 오류조립 본문 정상 반환
MongoDB 원본 오류기존 API 오류

Redis는 선택적 보조 캐시이므로 장애가 애플리케이션 전체 health를 DOWN으로 만들지 않는다. Spring Redis health indicator는 기본 비활성화하고 필요할 때 MANAGEMENT_HEALTH_REDIS_ENABLED로 다시 켠다. 앱 상태는 /actuator/health, Redis 상태는 컨테이너 health와 cache get/put error metric으로 분리해 관측한다.

Redis 장애 실험
  1. Redis 정상 상태에서 warm hit를 만든다.
  2. 부하 도중 실험용 Redis를 중지한다.
  3. 요청이 MongoDB 조립 경로로 성공하는지 확인한다.
  4. cache error, MongoDB 조회 증가, p95·p99를 기록한다.
  5. Redis 복구 후 miss → 저장 → hit 순서를 확인한다.
  6. 장애 중에도 앱 health는 UP, API는 200이고 cache error는 증가하는지 확인한다.

API 기반 증분 데이터 생성

Java initializer가 아니라 기존 perf/seed/seed_dataset.js가 실제 문서·커밋 API를 호출한다. COMMIT_BLOCK_CHANGE_RATE=0.1을 추가해 증분 저장 특성을 반영한다.

측정과 판정 규칙

주 지표

  1. p95
  2. 처리량
  3. MongoDB 조회 횟수
  4. 오류율

보조 지표

  • p99와 cold miss 회귀
  • heap·GC
  • Redis 메모리
  • 응답 payload
최소 의미 차이 = max(10%, baseline 3회 반복 변동폭)
3회 모두 같은 방향이고 최소 의미 차이보다 큰 결과만 개선으로 인정한다.
조건 식별자
결과는 .../<provider>/blocks-<count>/<pattern>/<load-profile>/run-<1|2|3>/에 저장한다. vus-20과 vus-50, rate-25-50-100-200를 별도 조건으로 취급하며 비교기는 --load-profile vus-20처럼 같은 load profile을 명시한 결과만 읽는다.
캐시 효과가 최소 의미 차이보다 작음캐시 미도입
Caffeine과 Redis 차이가 작음Caffeine
Redis가 성능·메모리에서 명확히 우수하고 Fail-Open 통과Redis
Redis 장애가 정상 조회를 실패시킴Redis 제외
실행 순서 편향 방지

JIT와 MongoDB warm-up 이점이 한 후보에 몰리지 않도록 순서를 교차한다.

  1. 캐시 없음 → Caffeine → Redis
  2. Redis → 캐시 없음 → Caffeine
  3. Caffeine → Redis → 캐시 없음

검증 전략

Seed

10% 신규 블록, 고정 blockOrders 길이, 결정적 변경 구간, 기존 100% 모드 호환성을 확인한다.

캐시 공통

miss→hit, key 격리, 예외 미저장, 동시 miss 1회 조립, 삭제 후 미반환을 확인한다.

실제 Redis

JSON 타입 보존, TTL, namespace, 중지·복구와 기존 인증 Caffeine 격리를 확인한다.

벤치마크 신뢰성
  • 로그인, seed, ID 탐색과 warm-up은 측정에서 제외한다.
  • 강한 부하에서는 status와 응답 크기만 검사하고 깊은 비교는 사전 검증에서 수행한다.
  • 각 후보 시작 전 로컬 Compose 앱을 해당 provider로 재생성하고 해당 캐시만 초기화한다.
  • none·caffeine은 Redis 없이, redis만 선택 profile Redis와 함께 실행한다.
  • 앱 재시작 중에도 seed가 유지되도록 Mongo 자동 정리와 JPA create-drop을 비활성화한다.
  • k6 setup 완료 뒤 before snapshot을 저장하고 gate를 해제해 준비 트래픽을 측정 delta에서 제외한다.
  • get의 hit·miss·error, put과 eviction의 success·error counter를 생성 시 0으로 등록해 이벤트가 없던 label도 명시적으로 보존한다.
  • 원본 k6 JSON, Git revision, JVM·캐시 설정과 자원 snapshot을 보존한다.
  • 3회 반복이 없으면 포트폴리오 성능 주장에 사용하지 않는다.

영향과 제외 범위

변경 영향

  • 커밋 본문 캐시 후보와 지표
  • API 기반 증분 seed 옵션
  • 커밋 조회 전용 k6 벤치마크
  • 현재 소스를 빌드하는 단일 로컬 앱 컨테이너
  • Redis 후보용 선택적 실험 컨테이너

변경하지 않음

  • API 요청·응답 계약
  • MySQL·MongoDB 스키마
  • 권한 정책과 커밋 생성 알고리즘
  • 다중 앱·HTTP 캐시·Snapshot 저장
실제 재조회 로그가 없으므로 Hot과 Mixed 결과는 민감도 실험이다. 운영 hit rate나 대규모 트래픽 처리 성과로 표현하지 않는다.

완료 조건과 다음 단계

  1. API seed가 10% 증분 데이터를 결정적으로 생성한다.
  2. 캐시 없음·Caffeine·Redis를 동일 조건에서 각 3회 비교한다.
  3. Cold·Hot·Mixed·Cold burst·포화점 결과와 Redis 장애 결과를 보존한다.
  4. 판정 규칙으로 캐시 미도입·Caffeine·Redis 중 하나를 선택한다.
  5. 선택된 후보의 운영 적용이 필요하면 별도 설계를 작성한다.
