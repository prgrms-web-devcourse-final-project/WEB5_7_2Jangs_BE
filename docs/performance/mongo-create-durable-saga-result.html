생성 Saga 로컬 성능 측정

작성일: 2026-09-04. 측정 대상은 커밋 생성이다. 스테이징 서버에는 요청하지 않았다.

판정

ID 목록을 자식 행 대신 JSON 한 컬럼에 저장하고 중복 조회를 제거한 뒤, 최적화 전 Saga 대비 중앙값이 50블록에서 27.0%, 200블록에서 51.3% 줄었다.

Saga를 적용하기 전 기준 코드보다는 중앙값이 각각 5.72ms, 5.27ms 늘었다. 사전 작업 기록과 완료 처리를 추가한 비용이 남아 있다. 현재 표본에서는 로컬 단일 요청 비용을 줄였다고 판단할 수 있지만 운영 부하에서도 괜찮다고 단정할 근거는 아니다.

조건

비교 대상은 기준 코드 78c3cb3, 최적화 전 Saga, 최적화 후 작업 트리다. 결과 폴더의 staging은 기준 코드의 이름이며 실행 서버는 모두 로컬이다.

각 버전에서 50블록과 200블록을 각각 한 차례 측정했다. 한 차례는 1 VU, 워밍업 3회, 본 측정 20회다. 총 본 측정 120회와 워밍업 18회가 성공했다. 로그인·문서 생성·그래프 조회는 setup으로 제외했다. 매 요청은 새 블록과 새 Idempotency-Key를 사용하므로 완료 결과 재사용 속도를 측정한 것이 아니다.

공용 블록 생성기와 perf/create/commit/commit_create_benchmark.js를 사용했다. 처음 요청별 2회만 실행했던 탐색 결과는 표본이 작아 최종 비교에서 제외했다. 추가 성능 실행 없이 기존 raw 파일의 commit_create_ms 값을 다시 확인해 이 보고서에 옮겼다.

측정 중 발견한 문제와 수정 과정

성능 회귀 발견

처음 로컬에서 50/200블록을 요청별 2회씩 실행하며 Saga 추가 비용을 살폈다. 이 탐색만으로 결론을 내리지 않고 버전별 워밍업 3회와 본 측정 20회 결과로 비교했다. 최적화 전 Saga의 중앙값은 50블록 33.405ms, 200블록 53.327ms였다. 기준 코드의 18.662ms, 20.706ms보다 느렸고 블록 수가 늘 때 지연도 크게 늘었다.

저장 구조와 중복 조회 확인

초기 구현은 정리할 MongoDB ID 목록을 @ElementCollection 자식 테이블에 저장했다. 200블록 커밋 한 건이면 작업 행 외에 블록 ID 200행과 CommitBlockSequence ID 1행이 추가됐다. 실제 측정 DB에서도 커밋 46건에 자식 행 5,796개가 남았다. 작업 기록 한 건을 추가하려던 설계에서 블록 수에 비례하는 행 쓰기가 발생했다.

기존 작업을 findExisting으로 확인한 뒤 MongoCreateOperationService.start에서 다시 조회하는 정상 요청 경로도 확인했다. 코드와 DB 행 수로 불필요한 쓰기·조회를 확인했지만 SQL별 소요 시간을 계측해 지연 기여도를 분리한 것은 아니다.

수정한 범위

MongoCreateOperation.mongoIds를 단일 JSON 컬럼에 저장하도록 바꿔 ID별 자식 행을 없앴다. 정상 시작 경로의 두 번째 기존 작업 조회도 제거했다. 동시에 같은 키가 들어와 INSERT가 충돌하면 기존 작업을 조회해 결과를 판정하는 처리는 유지했다.

MongoDB 쓰기 전 PENDING 저장, 도메인 데이터와 COMPLETED의 동시 커밋, 보상에 필요한 ID 기록은 그대로 유지했다. 응답 시간을 줄이려고 정합성 절차를 생략하거나 복구 timeout을 바꾸지는 않았다.

재측정 결과와 남은 비용

수정 후 중앙값은 50블록 24.387ms, 200블록 25.978ms로 줄었다. 최적화 전보다 각각 27.0%, 51.3% 감소했다. 다만 기준 코드보다는 각각 5.72ms, 5.27ms 느려져 Saga 추가 비용을 완전히 없앤 것은 아니다.

JSON 전환과 중복 조회 제거를 함께 적용했으므로 두 변경의 개선분은 나눠 판단하지 않는다. 이 결과는 로컬 순차 요청의 비용 완화를 확인한 것이며 운영 부하나 복구 Worker의 P1 경합을 해결했다는 근거는 아니다.

DB 기록으로 확인한 차이

최적화 전·후 Saga에서 각각 작업 행 48개를 확인했다. 커밋 46개와 setup에서 만든 문서 2개이며 모두 COMPLETED였다.

최적화 전에는 커밋 46건의 블록 ID 5,750개와 CommitBlockSequence ID 46개가 총 5,796개 자식 행으로 저장됐다. 최적화 후에는 해당 자식 테이블이 없고 JSON의 블록 배열 길이 50인 작업 23개와 길이 200인 작업 23개가 기록됐다. 23개에는 워밍업 3회가 포함된다.

이번 최적화는 JSON 전환과 정상 시작 경로의 중복 조회 제거를 함께 적용했다. 두 변경을 따로 측정하지 않았으므로 개선분을 각각 몇 ms라고 나눠 말할 수는 없다.

해석 범위

20개 표본에서는 중앙값과 p90을 우선 보고 p95는 참고값으로만 본다. 무작위 순서의 반복 라운드나 신뢰구간 검증을 하지 않아 실행 순서·JIT·캐시·로컬 자원 경쟁의 영향을 분리하지 못했다. 동일 프로세스 내 순차 요청이므로 표본이 서로 독립이라고 가정하지 않는다.

동시 부하, 장시간 실행, 운영 데이터 크기, 보상 적체, MySQL 장애 상황의 처리량은 측정하지 않았다. 문서·브랜치·병합 생성 성능에도 이 수치를 그대로 적용하지 않는다. 복구 Worker와 지연된 요청의 P1 경합은 별도 문제이며 이 응답 시간 측정으로 안전성을 입증하지 않는다.
