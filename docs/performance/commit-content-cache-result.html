k6의 동시 시작만으로 모든 요청이 조립 도중 겹쳤다고 보장하지는 않습니다. API 측정은 실행 시점의 working tree 변경을 포함해 hash만으로 재현할 수 없으므로, 최종 코드의 재현 가능한 근거는 latch로 실제 실행 겹침을 만든 동시 요청 20개 자동화 테스트입니다. 검산용 evidence는 perf/read/commit-cache/results/evidence/에 둡니다.

왜 @Timed가 아니라 직접 Timer인가

목표 지표는 cache hit까지 포함한 메서드 전체 시간이 아니라, miss일 때만 발생하는 MongoDB 조회·본문 조립 시간입니다. 그래서 CommitContentAssembler의 실제 조립 구간만 직접 Timer로 감쌌습니다.

Grafana에서 볼 지표

cache_gets_total, cache_evictions_total, cache_size, cache_puts_total, commit_content_assemble_seconds가 Prometheus에 실제 노출되는 것을 확인했습니다. hit ratio 하락, eviction 증가, assemble 재상승과 API p95를 함께 봅니다.

대응: 실제 트래픽에서 캐시가 손해라면 COMMIT_CONTENT_CACHE_ENABLED=false로 즉시 비활성화합니다. 최초 Cold 회귀 수치는 Caffeine만 재시작한 비대칭 조건이라 폐기했습니다. 랜덤 TTL은 동시 만료나 eviction churn 증거가 없어 이번 범위에 넣지 않았습니다.

다음 단계와 한계

  • Caffeine 채택은 실제 반복 조회 비율이 충분하다는 조건부 결정이다. hit ratio가 낮으면 비활성화한다.
  • cold miss와 초기 채움 p95는 Grafana에서 별도 위험 지표로 본다.
  • Cold 대칭 재측정은 평균 개선이 있었지만 반복 방향과 baseline 변동폭 기준으로 INCONCLUSIVE다.
  • staging 부하와 saturation은 사용자 지시에 따라 실행하지 않았다.
  • 수동 비교 구현은 62a2d19, 최종 어노테이션 구현은 8fab327, 성능 테스트 도구는 4f96481에 보존되어 있다.
  • 실제 운영 로그·트래픽 기반 증거는 없으며, 로컬 절대 수치와 운영 절대 수치를 합치지 않는다.
